# T-001 - Implementation Plan: Droid Companion VS Code Extension

## Phase 0: Project Setup & Foundation

### T-001 - Scaffold VS Code Extension Project
**Goal:** Create a minimal, buildable VS Code extension scaffold with TypeScript, esbuild, and test tooling.
**Scope:** Initialize package.json, tsconfig.json, esbuild config, Vitest config, ESLint/Prettier configs, and basic folder structure per architecture.md module boundaries.
**Acceptance Criteria:**
- `npm install` succeeds
- `npm run compile` produces a working extension bundle
- `npm run test` runs Vitest unit tests
- `npm run lint` and `npm run format` work
- Extension activates in VS Code Extension Development Host
**Tests:** Basic smoke test that extension activates without errors.
**Dependencies:** None.

### T-002 - Core Module Structure & Shared Contracts
**Goal:** Establish the module boundaries and shared TypeScript types/interfaces defined in architecture.md.
**Scope:** Create `core/` directory with: message protocol types (discriminated unions for webview↔extension), event bus/interfaces, scheduling primitives, and platform adapters for VS Code APIs (storage, commands, window, workspace).
**Acceptance Criteria:**
- All message types are versioned and validated at runtime (Zod or equivalent)
- Platform adapters are thin wrappers with no business logic
- No circular dependencies between modules
- Types compile in strict mode
**Tests:** Unit tests for message validation (valid/invalid payloads), event bus publish/subscribe, scheduler primitives.
**Dependencies:** T-001.

### T-003 - Persistence Layer
**Goal:** Implement typed persistence using VS Code storage APIs per architecture.md ownership rules.
**Scope:** Create `platform/storage.ts` with: settings (VS Code configuration), globalState (extension preferences), workspaceState (workspace-scoped transient), globalStorageUri (activity history/reports with versioned schema), SecretStorage (for future credentials).
**Acceptance Criteria:**
- Settings use documented defaults and respect workspace/user scope
- Activity history uses versioned JSON schema with migration path
- All reads/writes are typed; no `any` in storage layer
- Retention policy hook exists (configurable, default 90 days)
**Tests:** Unit tests for each storage adapter (read/write/delete, schema migration, retention cleanup).
**Dependencies:** T-002.

## Phase 1: Core Extension Infrastructure

### T-004 - Extension Entry Point & Activation
**Goal:** Wire the composition root in `extension.ts` with proper activation, command registration, and disposal.
**Scope:** Implement `activate()`/`deactivate()` in `extension.ts`: register webview view provider, commands, feature initializers; collect disposables; handle `onDidChangeTelemetryEnabled`.
**Acceptance Criteria:**
- Extension activates on `onView:droidCompanion` view registration
- All commands registered and discoverable in Command Palette
- `deactivate()` disposes all timers, listeners, watchers, subscriptions
- No memory leaks on repeated activate/deactivate cycles
**Tests:** Integration test for activation/deactivation; verify disposables are cleaned up.
**Dependencies:** T-002, T-003.

### T-005 - Webview Provider & Message Protocol
**Goal:** Implement the webview view provider with typed, validated message passing.
**Scope:** `companion/webview-provider.ts`: register view, handle `resolveWebviewView`, send initial state, validate incoming messages (reject unknown/malformed), serialize outgoing messages. Webview HTML/CSS/React entry point in `webview/`.
**Acceptance Criteria:**
- Messages are validated at runtime (not just TypeScript types)
- Unknown message types are rejected with non-sensitive diagnostic log
- Webview receives initial state on mount
- No secrets, full file contents, or unnecessary workspace metadata sent to webview
**Tests:** Unit tests for message validation (valid, malformed, unknown types); integration test for view registration and message round-trip.
**Dependencies:** T-002, T-004.

### T-006 - Webview React Scaffold & Base Components
**Goal:** Set up React in the webview with base layout, theming, and accessibility foundations.
**Scope:** `webview/src/`: React entry, CSS variables for VS Code theme colors, base `App` component, accessible focus management, reduced-motion media query hook, SVG icon system.
**Acceptance Criteria:**
- Webview loads without console errors
- Respects `prefers-reduced-motion` (animations disabled)
- Uses VS Code theme colors (works in light/dark/high-contrast)
- Keyboard focus visible and trapped correctly in modals/wheel
- No `retainContextWhenHidden` unless justified
**Tests:** React Testing Library tests for reduced-motion hook, theme color usage, focus management.
**Dependencies:** T-005.

## Phase 2: Well-being - Routines & Reminders

### T-007 - Routine Scheduling Engine
**Goal:** Implement the core routine scheduler (Pomodoro + custom work/break cycles).
**Scope:** `features/wellbeing/scheduler.ts`: state machine for routine (idle/running/paused/finished), configurable work/break/long-break durations, cycle counting, pause/resume/finish/reset, timestamp-based persistence for restart recovery.
**Acceptance Criteria:**
- Default Pomodoro (25/5) works without configuration
- Custom schedules accepted and validated
- Pause/resume preserves elapsed time accurately
- Extension restart reconciles from timestamps (no missed reminder replay)
- Long break triggers after N work cycles
**Tests:** Unit tests with injected clock: start/pause/resume/finish/reset, cycle transitions, long-break trigger, restart recovery, edge cases (zero/negative durations, clock jumps).
**Dependencies:** T-003 (persistence), T-002 (scheduling primitives).

### T-008 - Reminder System
**Goal:** Implement personal reminders (built-in + custom) with snooze, dismiss, quiet hours, and coalescing.
**Scope:** `features/wellbeing/reminders.ts`: reminder definitions (id, text, interval, enabled), scheduler integration, overdue coalescing, quiet hours (time range + timezone), snooze (fixed duration), dismiss, global off switch, persistence.
**Acceptance Criteria:**
- Built-in reminders: water, eye rest, stretch, short break
- Custom reminders with user-defined text/interval
- Snooze/dismiss/pause/quiet-hours/global-off all work
- No notification storm after sleep/reload/prolonged inactivity (coalescing + quiet hours)
- Reminders independent of routines (can enable/disable separately)
**Tests:** Unit tests with injected clock: interval firing, snooze, dismiss, quiet hours, coalescing overdue, global off, persistence/recovery, custom reminder CRUD.
**Dependencies:** T-007, T-003.

### T-009 - Well-being Settings & Commands
**Goal:** Expose well-being configuration via VS Code settings and commands.
**Scope:** `features/wellbeing/settings.ts`: configuration schema (routine durations, reminder intervals, quiet hours, tracking opt-in, retention), command registrations (start/pause/resume/reset routine, snooze/dismiss reminder, toggle tracking).
**Acceptance Criteria:**
- Settings appear in VS Code Settings UI with descriptions
- Commands work from Command Palette and keybindings
- Changes persist across reloads
- Tracking opt-in default is OFF
**Tests:** Unit tests for settings validation; integration test for command execution.
**Dependencies:** T-007, T-008, T-004.

### T-010 - Droid States & Action Wheel (UI)
**Goal:** Implement the four primary droid states, transitions, and radial action wheel in the webview.
**Scope:** `webview/src/components/`: `Droid` (SVG, four states + transition animations), `ActionWheel` (radial, pointer/keyboard/focus accessible, Escape closes, focus returns), `ActionList` (conventional fallback for reduced-motion/narrow/screen-reader), state mapping from extension messages.
**Acceptance Criteria:**
- Four states render: hanging out, working, resting/sleeping, helping/interacting
- Brief transition animations between states (respect reduced-motion)
- Action wheel opens/closes via click, keyboard, command
- Wheel actions: routine, reminders, reports, project scan, cleanup, rules
- Accessible fallback list works identically
- Escape closes wheel, focus returns to trigger
**Tests:** React Testing Library: state rendering, wheel open/close/keyboard navigation, fallback list, reduced-motion disables animations, focus management.
**Dependencies:** T-006, T-009 (commands for wheel actions).

### T-011 - Reminder & Routine UI Integration
**Goal:** Connect well-being engine to webview: show routine progress, reminder cues, and handle user actions.
**Scope:** Webview components for: routine timer display (work/break countdown), reminder indicators (subtle dot/animation per ui-behavior.md), callout with actions (mark done, snooze, dismiss, settings), message handlers for user intents → extension commands.
**Acceptance Criteria:**
- Routine timer updates in real-time (webview-local, synced from host)
- Reminder cues are calm (no red, no frantic animation by default)
- Callout offers relevant actions only
- User actions send validated messages to extension
- No chat UI for ordinary reminders
**Tests:** React Testing Library: timer display, reminder cue rendering, callout actions, message emission. Integration: extension receives and processes webview intents.
**Dependencies:** T-008, T-009, T-010.

## Phase 3: Well-being - Activity Tracking & Reports

### T-012 - Active VS Code Time Estimation
**Goal:** Implement opt-in active time estimation using coarse signals.
**Scope:** `features/wellbeing/activity.ts`: track editor interaction timestamps (focus, text change, save, command), inactivity threshold (default 5 min, configurable), pause/resume/disable, segment recording (not running counter), restart/clock-change/sleep-wake handling.
**Acceptance Criteria:**
- Tracking is opt-in (default OFF)
- No raw keystrokes, cursor positions, file contents, or clipboard stored
- Focus alone ≠ continuous activity; inactivity cutoff applied
- Segments stored as timestamps; durations computed on read
- Handles extension restart, VS Code focus blur, system sleep/wake, DST/timezone changes
- Described as "estimated active VS Code time" in all UI
**Tests:** Unit tests with injected clock/timezone: segment recording, inactivity cutoff, pause/resume, focus blur, restart recovery, DST transition, disabled state.
**Dependencies:** T-003 (storage), T-002 (platform adapters for VS Code events).

### T-013 - Daily & Weekly Reports
**Goal:** Calculate and serve daily/weekly summaries from local activity history.
**Scope:** `features/wellbeing/reports.ts`: daily summary (active time, sessions, cycles, reminder outcomes), weekly summary (daily breakdown, total, average, trend), missing data shown as missing (not zero), local calendar day boundaries, timezone handling, clear history action.
**Acceptance Criteria:**
- Daily report includes all specified fields
- Weekly report aggregates correctly with missing days
- Missing data explicitly shown as missing
- Day boundaries use local calendar; DST handled
- Clear history removes well-being records only
- No source code/project details in reports
**Tests:** Unit tests: daily/weekly aggregation, missing data, timezone/DST, clear history, trend calculation.
**Dependencies:** T-012, T-003.

### T-014 - Reports UI
**Goal:** Display daily/weekly reports in the companion view.
**Scope:** `webview/src/components/ReportsView.tsx`: daily/weekly tabs, estimated labels, missing data indicators, clear history button (with confirmation), accessible table/list layout.
**Acceptance Criteria:**
- Reports render with clear "estimated" labeling
- Missing days shown as gaps, not zeros
- Clear history requires confirmation
- Keyboard navigable, screen-reader friendly
- Respects reduced-motion
**Tests:** React Testing Library: report rendering, missing data display, clear confirmation, accessibility.
**Dependencies:** T-013, T-006.

## Phase 4: Repository Companion - Project Overview & Tree

### T-015 - Project Discovery & Scanner
**Goal:** Implement repository scanning with exclusions, incremental updates, and project signal detection.
**Scope:** `features/repository/scanner.ts`: discover workspace folders, detect project signals (package.json, lockfiles, framework configs, VCS), generate tree with depth/size limits, respect exclusions (gitignore, configured), incremental scan on file events (debounced), bounded diagnostic set.
**Acceptance Criteria:**
- Tree generated without network requests
- Excluded directories not crawled; contents not shown by default
- Project signals detected from local files only
- Incremental scans avoid full rescans
- File events debounced/batched
**Tests:** Unit tests (with temp fixtures): tree generation, exclusions, signal detection, incremental update, empty workspace, large repo performance baseline.
**Dependencies:** T-002 (platform adapters for fs/workspace), T-003 (workspaceState for scan cache).

### T-016 - Bounded Diagnostics
**Goal:** Implement the MVP diagnostic set (generated dirs, missing ignores, config contradictions).
**Scope:** `features/repository/diagnostics.ts`: explicit diagnostic categories with severity, evidence paths, explanations, suggested actions; findings dismissible; informational findings don't popup; "unable to determine" for ambiguous cases.
**Acceptance Criteria:**
- Diagnostics are explicit, bounded, and documented
- Each finding has category, explanation, evidence, severity, suggested action
- Informational findings don't trigger repetitive popups
- Ambiguous cases return "unable to determine"
- Findings can be dismissed per-session
**Tests:** Unit tests: each diagnostic category, dismissal, ambiguous handling, no false positives on subjective structure.
**Dependencies:** T-015.

### T-017 - Repository Tree & Diagnostics UI
**Goal:** Display project tree and diagnostics in the companion view.
**Scope:** `webview/src/components/RepositoryView.tsx`: tree with expand/collapse, depth limit, diagnostic badges, dismissible findings list, "Review findings" action per ui-behavior.md.
**Acceptance Criteria:**
- Tree renders with sensible defaults
- Diagnostics shown inline and in summary panel
- Findings dismissible; dismissed state persists per session
- "Review findings" opens detailed view (not popup chain)
- Keyboard accessible, reduced-motion respected
**Tests:** React Testing Library: tree rendering, diagnostic display, dismissal, keyboard navigation.
**Dependencies:** T-016, T-006.

## Phase 5: Repository Companion - Rules & Cleanup

### T-018 - Explicit Naming & File-Placement Rules Engine
**Goal:** Implement user-defined explicit rules with pattern matching and validation.
**Scope:** `features/repository/rules.ts`: rule schema (versioned, path patterns, conditions), validation on load/save, inference helper (suggests starter rules from existing patterns, requires user review/save), evaluation on file create/rename/save (debounced), violation reporting with rule reference.
**Acceptance Criteria:**
- Rules use versioned, validated configuration
- Inference suggests rules but requires explicit user save
- Evaluation debounced; no continuous rescans
- Violations explain the rule and suggest correction
- No auto-move/rename; no AI calls
- Unknown convention → quiet or "unknown"
**Tests:** Unit tests: rule parsing/validation, pattern matching, inference suggestion, evaluation debouncing, violation reporting, invalid config rejection.
**Dependencies:** T-015 (file events), T-003 (workspaceState for rules).

### T-019 - Safe Cleanup Engine
**Goal:** Implement preview + confirmed deletion for supported generated paths.
**Scope:** `features/repository/cleanup.ts`: target list (`.next/`, `node_modules/`, documented additions), size estimation (approximate allowed), preview (exact targets), confirmation required, pre-delete revalidation (workspace bounds, no path traversal, symlink safety), dry-run mode, per-target outcome reporting.
**Acceptance Criteria:**
- Preview shows exact targets, no filesystem changes
- Confirmation describes exact targets; only those attempted
- Unsafe paths (outside workspace, root, traversal, dangerous symlinks) rejected
- `node_modules/` only after explicit selection
- Dry-run available
- Outcomes: success/skipped/failed per target; partial failure ≠ full success
**Tests:** Unit tests (temp fixtures): preview generation, confirmation gating, path traversal/symlink rejection, workspace boundary enforcement, partial failure reporting, dry-run. Never delete real data.
**Dependencies:** T-015 (scanner for target discovery), T-003.

### T-020 - Rules & Cleanup UI
**Goal:** Expose rules editor and cleanup preview/confirmation in companion view.
**Scope:** `webview/src/components/`: `RulesEditor.tsx` (create/edit/validate rules, inference button), `CleanupView.tsx` (target list with sizes, preview, confirm, dry-run, outcome report).
**Acceptance Criteria:**
- Rules editor validates on input; shows inference suggestions
- Cleanup view shows targets, sizes, preview button
- Confirmation dialog describes exact targets
- Dry-run executes without deletion
- Outcome report shows per-target status
- Accessible, keyboard navigable, reduced-motion
**Tests:** React Testing Library: rules CRUD, inference flow, cleanup preview/confirm/dry-run, outcome display, accessibility.
**Dependencies:** T-018, T-019, T-006.

## Phase 7: Telemetry & Privacy

### T-023 - Telemetry Module (Opt-In Only)
**Goal:** Implement optional, consent-based product usage telemetry per privacy-and-telemetry.md.
**Scope:** `features/telemetry/`: event schema (allowlisted fields only), consent gate (extension setting + `env.isTelemetryEnabled`), queue with bounds, transport (using `@vscode/extension-telemetry` or compliant custom), privacy notice, opt-out clears queue.
**Acceptance Criteria:**
- Default telemetry OFF; requires explicit opt-in
- Respects VS Code `isTelemetryEnabled` (if VS Code telemetry off, extension telemetry off)
- Events use fixed schema: `extension_activated`, `feature_opened`, `feature_action_completed`, `operation_failed` with coarse categories + version
- No arbitrary payloads/logs attached
- Queue bounded; failed delivery doesn't retry indefinitely
- Opt-out stops sending + clears queue
- No backfill on opt-in
- Personal activity/reminder data not reachable from telemetry module
**Tests:** Unit tests: consent gate, VS Code telemetry disabled, queue bounds, schema allowlisting, opt-out clears queue, personal data isolation. Integration: no network calls when disabled.
**Dependencies:** T-003 (settings), T-004 (activation).

### T-024 - Privacy Controls & Data Lifecycle
**Goal:** Expose user-facing privacy controls and enforce retention.
**Scope:** Settings: telemetry opt-in/out, activity history retention (default 90 days, configurable), clear history command, privacy notice link. Implement retention cleanup on activation.
**Acceptance Criteria:**
- Retention policy enforced (configurable, default 90 days)
- Clear history removes well-being records
- Privacy notice accessible before telemetry opt-in
- Project rules: if saved to repo file, warn user it may be committed
- No accounts, sync, AI providers, web research in MVP
**Tests:** Unit tests: retention cleanup, clear history, privacy notice display. Integration: settings UI shows all controls.
**Dependencies:** T-012, T-013, T-023.
